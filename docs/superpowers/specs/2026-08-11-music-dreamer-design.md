# Music Dreamer 悦享音乐项目主体设计

- 状态：2026-08-18 已批准“薄而完整”加速范围及书面版本
- 日期：2026-08-11
- 当前范围：项目主体、测试与本地运行
- 后置范围：CodeArts、实训报告、答辩材料、真实 SMTP 与公网部署

## 1. 需求来源与事实边界

需求以登录后的 EduPlus 项目页、页面中的架构/功能/流程/界面图，以及 `项目素材/` 为依据。页面明确显示“老师暂时还没有发布实训指导”，且没有评分、截止、提交或附件说明，因此这些未知项不作为隐含验收条件。

本地素材只有图片、字体、少量样式、压缩包和一份 8 表 MySQL 脚本，没有可复用的完整前后端源码或音频。原脚本存在无盐 MD5 密码、缺少主键/唯一约束、跨域外键和邮箱激活字段缺失等问题，只继承业务含义，不原样作为成品数据库。

## 2. 项目目标

交付一个真实可运行、可持久化、可测试的音乐平台主体。2026-08-18 起采用“薄而完整”策略：保留主要用户可见能力和真实运行链路，以最小可靠实现完成闭环，不再为主体完成门槛增加复杂算法、可靠事件架构或穷举式加固。

- 管理员、歌手、普通用户三类角色拥有不同权限。
- 保留 Spring Cloud Alibaba、Nacos、Gateway、MySQL、Redis 和两个 Vue 前端等课程技术特征。
- 完成登录注册、邮箱激活、音乐搜索/基础推荐/播放、歌手发布、收藏、歌单、简单消息、上传下载及必要后台管理；个人设置只保留完成主流程所需字段。
- 音频播放、数据库写入、Redis 会话、服务发现和权限控制均走真实运行链路，不以静态界面或内存假数据代替。
- 用户端兼顾手机和桌面，后台以桌面工作流为主并保持基本响应式。

主体阶段不做真实外部邮件发送、CodeArts 发布、课程报告和答辩材料；这些在主体通过独立验收后再启动。

## 5. 五服务边界

### gateway-service

- 唯一外部 API 入口，按路径路由服务。
- 解析 Redis 会话、执行基础限流和路由级权限检查。
- 删除客户端提供的内部身份头，再注入可信用户 ID、角色和状态。
- 不持有业务数据，不聚合业务写操作。

### identity-service

- 用户注册、开发收件箱邮箱激活、登录、退出和会话管理。
- 当前保留注册所需资料、角色与账号状态；完整个人资料、头像和密码修改后置，仍归本服务所有。
- 管理员用户查询、角色调整和锁定/解锁。
- 拥有 `identity` schema。

### catalog-service

- 歌手资料、歌曲元数据、关键词搜索以及按热门或最新排序的基础推荐候选。
- 歌手发布/编辑歌曲，管理员审核、上下架和锁定歌曲。
- 标签偏好、播放计数事件和可靠 outbox 后置；既有表结构保留但不作为当前完成门槛。
- 拥有 `catalog` schema。

### interaction-service

- 音乐收藏、歌单、歌单歌曲和收听历史。
- 简单消息发布、用户收件箱和已读状态。
- 歌单关注、复杂未读统计、推荐偏好和可靠审计事件后置。
- 拥有 `interaction` schema。

### media-service

- 图片、音频和歌词上传、校验、元数据与下载。
- 支持 HTTP Range，满足音频拖动和续播。
- 文件保存在工作区外的可配置目录；数据库只存对象元数据和相对存储键。
- 拥有 `media` schema。

Nacos 是注册发现基础设施，不计入五个应用服务。MySQL 使用一个实例、四个 schema；服务禁止跨 schema 查询或建立外键。

## 6. 核心数据模型

### identity schema

- `users`：用户名、邮箱、手机、BCrypt 密码、角色、账号状态、资料与版本号。
- `email_activation_tokens`：令牌摘要、用户、过期时间和使用时间。
- Redis 会话：随机令牌摘要、用户 ID、角色、状态、创建/过期时间。

### catalog schema

- `artist_profiles`：歌手用户 ID、艺名、简介和状态。
- `tracks`：歌手用户 ID、名称、媒体对象 ID、封面 ID、歌词 ID、时长、状态和播放量。
- `tags`、`track_tags`：规范化标签关系。
- `outbox_events`：需可靠投递的审计和播放事件。

### interaction schema

- `track_favorites`：用户与歌曲唯一关系。
- `playlists`、`playlist_tracks`、`playlist_follows`：歌单及唯一关系。
- `listening_history`：用户、歌曲、播放位置和最近播放时间。
- `messages`、`message_receipts`：消息内容、目标范围、已读时间。
- `audit_events`：操作者、动作、对象、结果、时间和 trace ID。

### media schema

- `media_objects`：所有者、类型、原始文件名、存储键、大小、MIME、SHA-256、状态和创建时间。

所有主表使用明确主键、时间戳和乐观锁字段；所有关系表使用复合唯一约束。删除用户、歌曲和媒体默认采用禁用、下架或软删除，不让关联数据静默悬空。

现有 P0 数据库基线不因加速裁剪而回滚或删表。`tags`、`track_tags`、`outbox_events`、`playlist_follows` 和 `audit_events` 可暂不被应用服务使用；它们不是当前主体完成证据。

## 7. 关键业务流

### 注册与激活

1. identity 校验用户名/邮箱唯一性并创建未激活用户。
2. 生成高熵激活令牌，只保存摘要和过期时间。
3. 默认发送到应用内开发收件箱；SMTP 以后通过同一接口替换。
4. 激活成功后令牌一次性失效，用户才可登录。

### 登录与鉴权

1. BCrypt 校验密码，同时检查账号激活和锁定状态。
2. 生成高熵不透明会话令牌，Redis 保存摘要和 TTL。
3. Gateway 对保护路由查询会话并注入可信身份头。
4. 退出删除 Redis 会话；超时会话明确返回 401。

### 歌手上传与发布

1. media 将文件写入临时区并完成扩展名、MIME、魔数、大小、路径和 SHA-256 校验。
2. 校验通过后原子移动到正式存储并创建媒体对象。
3. catalog 引用媒体对象创建歌曲草稿，歌手提交发布。
4. 管理员审核后歌曲上线；任一步失败都保留可诊断状态，不返回假成功。

### 搜索、播放与收藏

1. music-web 经 Gateway 搜索 catalog。
2. 播放器从 media 获取支持 Range 的音频，并加载歌词和封面。
3. interaction 记录最近收听位置；播放量事件与跨服务计数后置。
4. 收藏和歌单写入由唯一约束保证重复请求幂等。

### 推荐

catalog 只提供确定性的热门或最新歌曲列表，并明确返回所用排序策略。标签偏好评分、跨服务个性化和 `POPULAR_FALLBACK` 降级编排后置，当前界面不得把基础列表标记为个性化推荐。

## 8. 一致性与错误处理

- 每个服务只对本 schema 开本地事务，不引入分布式事务。
- 当前核心写操作保持服务内本地事务；跨服务审计、播放计数 outbox 和重试投递后置。
- Feign 设置连接/读取超时；自动重试只允许幂等读取，不重试未设计幂等键的写操作。
- API 错误统一为 Spring `ProblemDetail`，包含稳定业务码、HTTP 状态、用户可理解消息和 `traceId`。
- 依赖服务不可用返回明确 503；权限不足返回 403；会话无效返回 401；校验错误返回 400；资源冲突返回 409。
- 日志不记录密码、令牌、激活链接、原始文件内容或其他秘密。

## 9. 上传与内容安全

- 服务端生成存储键，不信任用户文件名和路径。
- 图片只允许 JPEG/PNG/WebP，音频只允许经过确认的 MP3/WAV，歌词只允许受限大小的 UTF-8 LRC/文本。
- 扩展名、声明 MIME、实际魔数三重校验；限制单文件大小和用户配额。
- 文件目录不允许执行，Nginx 部署时只读映射。
- 歌词和简介默认按文本渲染；需要富文本时使用白名单清洗，禁止直接信任 `v-html`。
- 示例音频只使用用户提供或许可明确的免版权内容。

## 10. 前端设计

### music-web

- 一级结构：发现、搜索、歌单、我的和歌手工作台。
- 页面：登录/注册/激活、基础推荐、搜索结果、歌曲/歌手信息、播放器、收藏、歌单、简单消息和歌手上传。
- 真实 `HTMLAudioElement` 支持播放、暂停、进度、音量、单曲队列、Range 拖动和可用时的 LRC 同步；复杂队列编排后置。
- 桌面端使用稳定播放栏，手机端提供不重叠、可完成主流程的响应式播放器；独立全屏播放器和多设备像素级适配后置。

### admin-web

- 页面：用户管理、歌曲审核/管理和简单消息发布；独立歌手管理、概览统计和审计日志后置。
- 采用侧栏与表格布局，保留必要分页、空状态、危险操作确认和结果反馈；高级组合筛选后置。

### 视觉与可用性

- 保留课程参考图的信息结构，不做像素复刻。
- 使用中性底色、黄色播放强调色和绿色可用状态，避免单一色调和营销式大卡片。
- 使用素材中的合法图片与字体；按钮优先使用兼容 Vue 2 的 Lucide 图标并提供工具提示。
- 保留可见焦点、基本颜色对比和手机/桌面响应式；平板专项与全面无障碍审计后置。
- Vuex 只建立主流程实际需要的 `auth`、`player`、`catalog` 和 `library` 状态；前端路由守卫不替代后端鉴权。

## 11. 测试与验收

### 后端

- 单元测试：权限规则、核心状态机、文件校验以及收藏/歌单幂等逻辑。
- 服务集成测试：使用专用 MySQL schema 和 Redis 数据库验证真实迁移、事务与缓存行为。
- 契约测试：Gateway 路由、Feign 请求/响应和 `ProblemDetail` 错误结构。
- 启动验收：五个服务在 Nacos 注册为健康实例，所有外部 API 只能经 Gateway 完成关键流程。

### 前端与端到端

- 聚焦测试：登录、播放器、收藏、歌单、上传审核和危险管理操作。
- Playwright：管理员、歌手、普通用户各一条主流程；桌面覆盖三条流程，手机只覆盖普通用户主流程，并检查控制台错误。
- 媒体验收：合法文件上传与播放成功，伪装文件、超限文件和路径穿越三个关键拒绝场景通过。
- 持久化验收：重启应用后用户、歌曲、收藏、歌单与最近播放位置仍存在；消息只验证真实写入和读取。

### 主体完成门槛

1. 五个服务、MySQL、Redis、Nacos 与两个前端可通过受控脚本启动和停止。
2. 普通用户“注册激活 -> 搜索播放 -> 收藏/歌单 -> 读取消息”、歌手“登录 -> 上传 -> 提交歌曲”和管理员“登录 -> 审核歌曲 -> 管理用户/发布消息”三条关键流程通过，关键越权测试被拒绝。
3. 真实音频支持播放和进度拖动，歌词/封面正常加载。
4. 注册、上传、审核、收藏、歌单和最近播放等核心写操作真实持久化；重复收藏和重复添加歌单歌曲具备幂等或冲突处理。
5. 后端测试、前端测试、构建和 Playwright E2E 独立重跑通过。
6. 关键页面在桌面及普通用户手机主流程中无空白、重叠或文字溢出。

## 12. Codex 与 OpenCode 协作

- Codex 是集成者，拥有根配置、数据库迁移、共享契约、Gateway、主分支和最终验收。
- OpenCode 首阶段只拥有独立 worktree 中的 `catalog-service` 与 `media-service`；前端阶段重新分配目录。
- Codex 同期拥有 `identity-service`、`interaction-service` 和 Gateway。
- OpenCode 不修改根 POM、数据库迁移或共享契约；契约变更通过 handoff 提交给 Codex。
- 每个写者只在自己的 Git worktree 运行会生成文件的构建和测试。同一文件同一阶段只有一个写者。
- handoff 必须包含提交哈希、文件范围、命令结果、已知风险和契约变更请求。
- 集成时先停止并行写入，再由 Codex 检查 diff、合并并在主工作区独立重跑关键验收。
- Codeg 作为受监督的执行层使用；通过短阶段、Git checkpoint 和结构化 handoff 支持中断恢复，不宣称具备无人值守编排保证。

## 13. 实施阶段

1. **P0 基线**：Git、忽略规则、父工程、共享契约、四 schema 迁移、Nacos/MySQL/Redis 启停脚本与失败测试骨架。
2. **P1 身份链路**：注册、开发收件箱激活、登录/退出、Gateway 会话鉴权、用户与权限管理。
3. **P2 音乐纵向链路**：catalog、media、歌手上传发布、关键词搜索、Range 播放和后台审核。
4. **P3 最小互动域**：收藏、歌单、最近播放和简单消息。
5. **P4 双前端**：覆盖三角色核心流程的 music-web、admin-web 和基本响应式播放器。
6. **P5 主体验收**：构建、关键上传安全、服务注册、重启持久化、主流程 Playwright 和缺陷修复。

每个新增生产行为仍先写可失败的聚焦测试，再写实现。阶段内只运行受影响模块测试；P2、P3、P4 checkpoint 和 P5 才运行相应全量回归，避免每个小改动重复支付完整环境成本。主体通过 P5 后，另行讨论所有后置项。

## 14. 已锁定决策

- 薄而完整的课程主体，本地优先；加速裁剪范围以本文“加速范围边界”为准。
- 五服务领域拆分。
- Java 21 + Spring Boot 3。
- 两个前端统一 Vue 2.7。
- 保留课程结构并现代化界面。
- BCrypt、不透明 Redis 会话、开发收件箱、受控本地媒体存储。
- Codex/OpenCode 独立 worktree、单写者、结构化 handoff 和主分支独立验收。
- 不回滚既有数据库基线；被后置的表和字段保留但不计入当前完成门槛。
